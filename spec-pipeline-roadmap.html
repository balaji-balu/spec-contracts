Spec Pipeline Roadmap

How the pipeline goes from contracts on paper to specs your teams build from. Each milestone is a thin slice that ends in something running and evaluated on real cases, so every step can change the next. Nothing is built that can't yet be measured.

  • 7milestones, M0–M6
  • 1done (M0 contracts + evals)
  • M1next: one real agent
  • 6decisions to make along the way

How the roadmap is cut

  • Riskiest judgment firstRequirements analysis is the step most likely to be wrong and the cheapest to measure, since seeded recall needs no human. So it goes first.
  • Every milestone ends in an evalExit criteria are suite results from evals/thresholds.yaml, not "feature complete".
  • Humans are budgetedBA and architect time goes to labelling and approvals, and it is named in each milestone so it can be planned.
  • Decide when first neededOpen decisions carry the milestone that forces them. Until then they stay open.

Sequence

The critical path runs M1 → M3 → M4 → M5 → M6. M2, the judge, runs alongside M1 because the requirements phase can't gate on a judge nobody has calibrated.

M0

Contracts and eval harness

donethis conversation

Proves the pipeline can be specified precisely enough to verify mechanically and evaluate consistently.

Delivered

  • Scenario walkthrough (page, Excalidraw, Mermaid)

Carried forward

  • Prototypes are throwaway. The real tools are TypeScript pi extensions
  • Nothing has run against a real model yet
M1

One real agent

next≈ 2–3 weeks

Proves a pi agent can do real requirements analysis inside the contracts, and that we can measure how well it does. No reconciler yet: the agent is driven straight from the pi SDK.

Build

  • spec-lint in TypeScript: the full rule set, git-aware pins (H3/H4), shipped both as the validate_artifact pi extension and as a CLI
  • pi extensions: trace_link, term_lookup, and kb_search/kb_get over a file-based KB
  • req-analysis prompt and skill, AGENTS.md, and the first pipeline.lock.yaml
  • litellm gateway in front of every call, with traces and cost per run
  • Scorer ported to TypeScript and a suite runner for k = 3

Exit criteria

  • SD-RA-0001 at release thresholds: blocker recall 1.0 and recall.all ≥ 0.85, worst of 3 runs
  • One more seeded case written from a real past spec
  • A baseline report committed, with cost and tokens per run
  • Lint prototype retired
BA ≈ ½ day: write the second seeded case from a spec they know went wrongDecide: generator model, KB location
M2

A judge you can trust

parallel with M1≈ 1–2 weeks + labelling

Proves the eval gate's scores agree with your BA and architect well enough to block on, starting with the requirements rubrics.

Build

  • Judge pi session: rubric loader, constitution articles turned into criteria, output validated against the schema
  • Labelling sheet: artifacts stripped of provenance, scored blind with the same anchors
  • Calibration report: κ per criterion, bias checks, advisory or calibrated status

Exit criteria

  • JF-REQ-0001 sent back and JF-REQ-0002 passed, 3 runs out of 3
  • RQ-1, RQ-3 and CONST-ART-2 calibrated (κ ≥ 0.6 and ≥ 0.8 × human ceiling)
  • Every other criterion recorded as advisory, with its κ
BA + architect ≈ 2 days each: label 30 requirements and 30 requirements-analysis artifactsDecide: judge model (must differ from the generator)
M3

Requirements phase, end to end

planned≈ 4–6 weeks

Proves the reconciler can carry a spec from the user's words to approved requirements with real PRs, real people and the gates in place.

Build

  • Reconciler v0: state derivation, next-step rules 0–11, branches and PRs, commit trailers, loop limits
  • Comment commands (/answer, /accept-risk, /revise…) and CODEOWNERS gates
  • Intent agent over pi RPC with ask_user. The first UI is PR comments plus a chat CLI
  • DDD agent (strategic) with cml_check running ContextMapper in CI
  • Eval mode with the simulated reviewer

Exit criteria

  • G-0001 through requirements: ref_coverage ≥ 0.85, must_miss 0
  • CS-0001 req_stability ≥ 0.75. ADV-0001 passes every assertion
  • One new real spec, not the refund case, taken to approved requirements with your BA
BA ≈ 1 day: drive a real spec through PRsDecide: git host, one PR per phase vs per spec (D7), stale pins block or warn
M4

Design phase

planned≈ 3–4 weeks

Proves the pipeline produces designs an architect approves, keeps the boundaries intact, and can send problems back to requirements.

Build

  • Design-analysis, DDD (tactical) and design-generation agents
  • Back-edges: /confirm, blocked-by labels, change-request mode, re-run on stale pins
  • Boundary check (D9) and CML generators (PlantUML) for review
  • Design and design-analysis rubrics calibrated with the architect

Exit criteria

  • SD-DA-0001 at release thresholds, including the rate-limit trap
  • SPEC-0001 fully regenerated by the pipeline and approved by the architect
  • One back-edge exercised end to end on a case
Architect ≈ 2–3 days: labelling plus approving real designsDecide: domain/ ownership model (D6)
M5

Pilot with one team

planned≈ 4–6 weeks, mostly calendar

Proves the pipeline helps on real work, with the runtime gate live, a thin UI, and costs within budget.

Build

  • UI v1: a thin client with the artifact, findings and metrics panes, where buttons map to PR actions
  • Metrics dashboard over metrics.json and the litellm traces
  • Monthly drift re-labelling for the judge
  • Suites grown from pilot misses

Exit criteria

  • 3–5 real specs approved through the pipeline
  • BA and architect time-to-approve measured and accepted
  • Cost and wall time within budgets
  • Pilot retro, with D6–D13 settled
One team: BA, architect, 2–3 requestersDecide: promote the proposed decisions, or change them
M6

Execution handoff and the lagging loop

planned≈ 6–8 weeks

Proves good-scoring specs actually lead to less rework, which closes the measurement loop you asked for at the start.

Build

  • Plan → code → QA consumes only tagged specs and adds implements/tests links
  • Lagging signals attributed to IDs: clarification requests, spec-rooted rework, escaped defects
  • Correlation report between leading metrics and lagging-signal density
  • Flywheel: every spec-rooted miss proposes a seeded case

Exit criteria

  • Pilot specs implemented through the loop
  • First evidence of which leading metrics predict rework, and which ones to drop
  • At least 5 curated cases added from real misses
QA lead: root-cause tagging (spec vs code)Decide: execution harness shape (same reconciler or a separate loop)

Later: the platform horizon

These come from the wider platform vision and follow once the spec pipeline is proven. Each gets its own contracts-first pass.

  • Control planePolicy, permissions, agent registry and governance above the reconciler.
  • Typegraph as the trace storetrace.yaml stays the source, synced into the knowledge graph for querying intent-to-code links.
  • Product loopThe long-running agent that watches requirements, design and code for drift and flags it to a human.
  • Reverse engineeringCode → spec, using the same contracts, so existing systems can join the pipeline.
  • Live architecture viewsC4 and deployment diagrams generated from CML and design artifacts.
  • Enterprise levelDeferred by choice until system and architecture levels are proven.

Effort figures assume two engineers who already know pi and TypeScript. Treat them as relative sizes. Real dates come after M1, once there is a baseline.
